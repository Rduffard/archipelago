# Sanguine Archipelago Phase 3 architecture audit

## Executive summary

Use one independent package, `@crossworld/sanguine-engine`, with a dedicated `training/` module. Today the Express backend is authoritative for saved characters, campaign permissions, and commands. It already has useful rules seams, especially ledger replay and the equipment and combat helpers. The largest barrier is a 33-file circular dependency spanning the rule registry, equipment, and feature handlers. Moving the existing rules directory intact would bring that cycle, Node-specific facilities, and HTTP error conventions into every consumer.

Extract behavior in tested slices. Start with attributes, dice, point buy, and Training. Break registry and equipment import cycles before moving progression or active commands. Keep the persisted `SA-CHAR-1` contract stable through package integration. Treat terminology, persisted-field changes, and production debug cleanup as separate cutovers. The proposed stages and their acceptance gates are in the [migration plan](phase3-migration-plan.md).

## Current application boundaries

- **Backend.** `src/routes/index.js` mounts the Archipelago module alongside other Crossworld apps. `src/modules/archipelago/routes.js` applies shared authentication. `characters/routes.js` mounts create, preview, read, delete, commands, and audit endpoints. The ledger is replayed by `system/rules2024/engine.js`; live resources and feature journals are projected by `runtime.js` and `selections.js`. Character commands own the transaction and apply the result to MongoDB. The practice combat store has its own state machine and owner-scoped revision updates.
- **Frontend.** `src/routes/AppRoutes.jsx` mounts a protected React shell with roster, creator, persistent sheet, map, campaign pages, and two visible test surfaces. Creator and sheet fetch `/archipelago/system/character-rules?version=SA-CHAR-1`. They use backend preview and command responses. Local sheet rolls resolve rules in the browser and produce a local history. The character, campaign, and practice encounters have separate request paths.
- **Persistence.** `characters/model.js` stores `schemaVersion`, `rulesVersion`, `rulesLedger`, `rulesRuntime`, `documentRevision`, inventory, loadout, and integer copper. Several structures use Mongoose `Mixed`; model validation replays the ledger and verifies equipment and runtime. Character and campaign registration writes use transactions. Session hosting and joining are campaign-authorized. `combat/model.js` persists isolated owner-scoped practice snapshots; it is separate from the campaign/session workflow.

## Training ownership

`system/trainingChecks.js::proficiencyBonus` validates levels 1–20 and applies the same formula as `engine.js`'s inline bonus. Equipment attacks and practice attacks call the helper, while the character replay uses the inline value to derive saves, skills, initiative and spell statistics. `trainingCheckModifier` is exported with no tracked source or test caller found. `equipment/training.js` builds Calling defaults and weapon-group membership from the catalog; `equipment/index.js` evaluates current loadout restrictions. Creation and progression compose grants in `engine.js`, `creation.js` and the catalog. `toolChecks.js` normalizes legacy tool IDs, applies one Training term, and grants Advantage when both the skill and tool are trained. `agilityChecks.js` has a separate specialized tool/skill adjustment and `selections.js` recomputes Rage skill modifiers. The frontend already receives `trainingBonus`, skill/save modifiers and Expertise, then consults Training again for effects such as Reliable Talent.

- **Training owns** the bonus schedule, grant aggregation and eligibility, exact/category/group weapon membership, armor and shield membership, stable tool aliases, skill/save membership, and the untrained/trained/Expertise contribution. Feed in Calling, Path, background, feat and other grant definitions. Keep Training logic independent of the full rules registry and derive weapon membership from item tags or a supplied group index.
- **Consumers own** the surrounding domain rules. Attributes own score modifiers. Checks own combining Training with conditions and rolling. Combat owns action legality and attack resolution. Equipment owns loadout and consequences of missing armor Training. Progression owns the level schedule and prerequisites, and supplies acquisition choices to Training. Magic owns spell formulas and restrictions. The UI displays the resulting breakdown and eligible choices.
- **Contract transition.** Keep `training`, `expertise`, `equipmentTraining`, `trainingBonus`, existing grant IDs and persisted choices. A serialized practice attack event uses `proficiency`, read by `CombatTestPage.jsx`. Adapt that field on read or retain it for the old wire version; change the UI label independently. Scope any aliases to legacy shapes. Test level boundaries, initial versus later Calling grants, no double bonus for trained skill plus trained tool, Expertise, armor/shield restrictions, weapon groups, and reload of older practice logs. Expertise remains the existing name for enhanced Training.

## Backend seams and confirmed verification gap

- `characters/commands.js` combines envelope validation, mechanical dispatch, facts from saved state, permission checks, target resolution, compare-and-set writes, and receipt persistence. Keep actor/target authorization, identity, transaction callbacks, operation digests, receipts and state publication in Express. Move deterministic eligibility and effect calculation behind typed transitions. Keep cross-target reads, treatment locks and rollback atomic. Mechanical validation stays enforced server-side even when the browser can preview it.
- `characters/rules2024.js::reconcile` applies mechanical advancement and preservation policy inside a persistence adapter. Pull it out with fixtures that cover depleted Health/pools/slots, temporary grants, spell preparation and rest or encounter state. `model.js` can still call an engine invariant validator. Keep strict document validation, schema/indexes, and query/update policy in Mongoose. Current model hooks and direct CAS updates follow different paths, so test the effective constraints for both.
- The blueprint is assembled at import time and hashed with Node crypto. The active catalog serializes to 1,024,319 bytes before transport compression. `system/routes.js` mixes the versioned catalog, convenience blueprint and preview compatibility routes. Keep HTTP status/error mapping, version negotiation and ETags in the adapter. Preserve hash and response behavior through the initial integration. Measure and separately address catalog loading when designing browser-facing exports.
- Keep authentication, campaign membership and GM authority, session secrets and visibility, persistence and owner-specific practice controls in the application. `combat/state.js` currently mixes owner checks, revision/retry mechanics and rule resolution. Keep storage CAS and external ownership in the backend and move rules into plain-state transitions. Sessions should eventually attach encounters through a host adapter, with no change required by the extraction itself.
- **Confirmed CI gap, medium severity.** Backend `.github/workflows/ci.yml` runs `npm test --if-present`; `package.json` has no `test` script. `npm run` lists lint, start and dev only. Establish explicit suite commands in Stage A and demonstrate that an intentional failing fixture fails CI before relying on it for parity gates.

## Dependency and coupling analysis

- The backend graph reaches 152 of 157 runtime files from `src/app.js`. The major strongly connected component spans 33 files. For example, `equipment/index.js` consumes rules replay and equipment Training, `rules/selections.js` consumes equipment, and the aggregate registry loads feature and item operations. Lazy `require` defers several edges. Break the loop with leaf catalog reads, a Training grant input, and explicit fact/summary inputs to operations before moving modules. Callers should import public package subpaths, with no new cycles among rule modules.
- The frontend graph reaches 92 of 98 runtime files. The one static cycle is `MapCanvas.jsx`, `AuthoredShapeLayer.jsx` and `ShapeEditorLayer.jsx`. The frontend parity suites currently deep-import sibling backend source via `../../crossworld_backend/...`; this makes a clean standalone test checkout depend on folder placement. Replace those imports with package entry-point checks and independent fixtures. There were zero unresolved literal relative paths in the index.
- All five frontend runtime dependencies have a source importer. Backend `cloudinary` and `multer` have no source/test/config import found and are candidates for removal after shared-app regression checks. Treat ESLint, Vite, nodemon and type packages as tooling dependencies. Review whether the React type packages are needed for editor/tool support before considering removal. React, Vite, Express and Mongoose versions and Node constraints are listed in the evidence index. Both `npm outdated` checks returned `ENOTCACHED` in the registry's cache-only mode, so latest available versions are unverified. Dependency security advisories were outside this audit.
- Frontend is ESM with Vite 8.0.7 locked, requiring Node `^20.19.0 || >=22.12.0`. Backend is CommonJS, with ESLint 10 requiring `^20.19.0 || ^22.13.0 || >=24`. Frontend deploy specifies Node 20, backend CI specifies 22, and backend deploy uses the VM's existing runtime. The common audited runtime was Node 22.17.1. Pin a supported shared Node 22 release for package and consumer checks, and verify the actual VM version before changing its production install path. Independent app tool versions can stay isolated.
- Portability blockers include `node:crypto` in dice, rules, equipment, and the registry, `node:util` in practice replay comparison, `Date.now()` fallback in `rules/clock.js`, and HTTP status errors in operation modules. Browser `window`, `localStorage`, `import.meta.env` and request authorization belong to app adapters. `structuredClone` and the JSON catalog load path need coverage in the selected Node, browser and desktop runtimes.

## Proposed package architecture and Loom boundary

| Internal module | Owns |
|---|---|
| `core/dice`, `core/attributes`, `core/checks` | Dice records and selection, score modifiers, check and save composition |
| `characters/`, `progression/` | Creation and replay contracts, derived character state, level events and advancement reconciliation |
| `training/` | Bonus, eligibility, grant resolution, aliases and Expertise |
| `callings/`, `paths/`, `abilities/` | Calling/Path definitions, feature schedules, feat and feature execution dispatch |
| `equipment/`, `resources/` | Item data, loadout, economic and gear rules, pools, recovery and rest |
| `combat/`, `magic/`, `encounters/` | Attack/damage and turn economy, casting and timed effects, participant snapshots and encounter transitions |

Start with public operations for catalog read, character preview/replay, sheet checks and validated character/encounter commands. Expose additional subpaths only for real consumer needs. Catalog data must avoid importing dispatchers. Callers pass plain state and permitted facts, with narrow capability inputs for dice, time and IDs. Use host time with an explicit unit and distinguish in-world time from wall time. Return next state, typed outcomes and domain errors; adapters translate errors and own storage. Use an immutable input contract at the transition boundary, even if existing rule handlers mutate a private working copy. For retry/replay, record actual dice, event IDs and authoritative time with accepted events. A receipt replay must return the first accepted result without rerolling. Hashing and idempotency belong at the host boundary unless a specific persisted rule fingerprint requires a portable deterministic implementation.

The website may run a local preview/check with the shared resolver. Express supplies trusted dice and facts for multiplayer saves. Loom's host can call the same transitions and publish accepted state/events to browser players; desktop and single-player hosts can supply equivalent inputs and persist locally. Distinguish engine rules events from audit receipts and client log rows. Use opaque participant IDs and confirmed target or spatial facts. The current practice state uses fixed actor/target assumptions and a separate action model; it is evidence for attack primitives, not the general Loom encounter protocol.

## Baseline and completion gates

See [verification baseline](phase3-verification-baseline.md) for current results, historical provenance, test ownership and outstanding characterization. The main implementation blockers are the rule/equipment cycle, the serialized legacy ledger discriminator, and lack of one shared turn contract for the two combat workflows. The main release gates are equivalence on saved characters, an independent install/build in both consumers, real-store transaction/restart verification, and provenance review of distributed data.

The extraction order is pure leaves and Training, then catalog/creation/progression, equipment and resources, active combat/magic/features and encounter transitions, backend integration, frontend integration, then compatibility and debug cleanup. Implementation starts only after review of this audit and its [stage-by-stage plan](phase3-migration-plan.md).
